# Through the lens

A WebGPU example that reads an image through a short compute graph on luma's `GPUCommandGraph`:
luminance, blur, gradient and a per-column skyline, each stage a graph node whose output stays in a
GPU buffer. The canvas shows the five stages (image, luminance, blur, gradient, skyline) as vertical
bands of one picture, and the infobox prints a plain-text "Graph readout" of the nodes, the GPU time
per node and the dispatch count.

The examples resolve `@luma.gl/*` and `@deck.gl/*` from this repository's vendored tarballs (`vendor/`), so run them from this repository (after `npm install` at the root); they are not meant to be copied out on their own.

Run `npm start` in this folder (npm puts the ancestor `node_modules/.bin` on `PATH`), or run
`npx vite examples/gpgpu/photo-graph` from the repository root. No network access is needed.
`npm run test:visual` runs `scripts/visual-smoke.mjs` (in Rigi, wrap it in
`node scripts/gpu/with-render-lock.mjs --`).

## What it does

1. **Image.** A 640 x 400 test image (sky, low sun, three ridges) is painted with Canvas 2D at
   start-up and uploaded as one `u32` storage buffer of packed RGBA. It is generated, not a photo, so
   the example ships no image asset.
2. **Graph.** One `GPUCommandGraph` declares four compute nodes. Dependencies are inferred from each
   node's declared buffer uses:

   | Node | Work |
   | --- | --- |
   | `luminance` | Rec. 709 luminance per pixel into an f32 buffer. |
   | `blur` | 5 x 5 box blur with clamped edges. |
   | `gradient` | Sobel gradient magnitude of the blurred luminance. |
   | `skyline` | One invocation per column: the first row from the top whose gradient exceeds the threshold (the image height when none does). |

   The application creates the command encoder, submits, and reads the four outputs back with
   `Buffer.readAsync` to paint the bands on a 2D canvas. `GPUCommandGraphInspector.observeGraph`
   records each encoding. When the device has `timestamp-query` (the device is created with
   `featureLevel: 'max'`), the encoder gets a `timeProfilingQuerySet` and the readout lists GPU
   milliseconds per node; otherwise it shows the submit-to-readback wall time for the whole graph.
3. **Readout.** `encoding.stats` provides the node list and outcomes, `computePassCount` and the
   executed-node count. "dispatches" is the number of executed compute nodes (one `Kernel.dispatch`
   each); "passes" is the number of physical compute passes the graph opened, which can be lower
   because the graph coalesces adjacent compute nodes.

The edge threshold slider re-runs the compiled graph with a new uniform; nothing is recompiled.
"Bring your own lens" reads a photo you pick through the same graph: it is center-cropped to
640 x 400 on a 2D canvas and written into the `pixels` buffer, then the graph runs again. The photo
stays in the page.

## Verification

`scripts/visual-smoke.mjs` (not yet run) checks that the four nodes ran in order with four
dispatches, that the skyline is found in more than 90 % of the columns and lies on the ridges, that
an unreachable threshold finds no edge, that `finalize()` is idempotent, and that `?backend=webgl`
shows the "requires WebGPU" message instead of failing.

## Upstream notes

API observations from this example, shared with `gpgpu/horizon-graph`:

- **Compute nodes need both `compile` and `compileAsync`.** A node built from `Kernel.createAsync`
  has to duplicate the synchronous path (`makeKernelCompiler` here). A
  `GPUCommandGraph.addKernelPass({kernel, bindings, workgroupCount})` helper would remove the
  boilerplate.
- **Per-node GPU timings need a hand-sized `QuerySet`.** The graph knows its node count, so it could
  size or own the query set.
- **Adjacent compute nodes coalesce into one pass.** `encoding.stats.computePassCount` reports it,
  but there is no per-node record of which pass a node joined, so a readout can show dispatches and
  passes only as two totals.
