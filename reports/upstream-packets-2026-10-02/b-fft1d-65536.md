## Title

`feat(gpgpu): GPUFFT1D lengths up to 65536`

## Problem

`GPU_FFT1D_MAX_LENGTH` is the shared `GPU_FFT_MAX_LENGTH = 2048`, so `getGPUFFT1DSupport(device, {length: 8192})` reports "must be from 2 through 2048" and the `GPUFFT1D` constructor path refuses it. Nothing in the 1D implementation needs the limit: every pass is a global-memory radix-2 butterfly (no workgroup storage), so only the shared constant bounded the length. `GPUFFT2D` and `GPUConvolution` do have reasons to keep 2048 (their row / column kernels), and keep it.

Rigi needs 8192-point transforms (360 degree yaw correlation of a skyline, `src/lib/refine/fft-gpu.ts`) and longer ones for the horizon; today it splits them into a four-step 2048-point scheme with a 512-point retry and a spot check.

## Minimal repro

On master, no GPU needed:

```ts
import {getGPUFFT1DSupport} from '@luma.gl/gpgpu/gpu-core';
getGPUFFT1DSupport(device, {length: 8192}).reason; // "... must be from 2 through 2048."
```

With a device: `repro/fft-dawn.node.spec.ts.txt` (see packet a) runs lengths 8 to 65536 and only reaches 8192 and 65536 with this patch.

Measured (Dawn / Metal, this Mac; this patch plus packet a): forward vs float64 FFT relative error 4.7e-7 at 8192 and 3.1e-7 at 65536. Rigi's rigi.6 run (batch 2): 1.9e-7 / 4.5e-7 / 3.3e-7 at 2048 / 8192 / 65536, inverse round trip at most 1.3e-6. Without packet a, Metal results at these lengths are wrong (relative error about 1 in Rigi's pre-fix run).

## PR description (luma template)

```markdown
For # (open an issue first per the template; none filed)

#### Background

`GPUFFT1D` accepts power-of-two lengths from 2 to 2048 only because it reuses the constant shared with `GPUFFT2D` and `GPUConvolution`. Applications with long signals (audio, skyline correlation, horizon profiles) have to split transforms by hand.

#### Rationale

The 1D passes are global-memory radix-2 butterflies with no workgroup storage, so the length is bounded only by buffer and binding limits, which `getGPUFFT1DSupport` already checks. Separate 1D and shared limits keep the 2D / convolution behaviour unchanged.

#### Change List

- `GPU_FFT1D_MAX_LENGTH = 65536`; `GPU_FFT_MAX_LENGTH` (2048) stays for `GPUFFT2D` and `GPUConvolution`
- `getGPUFFTLengthReason(..., maxLength?)`
- Chunked path: block scratch holds `max(4096, length)` complex rows, within the binding and buffer limits
- Update the `GPUFFT1D` docs and node spec
```
