  Needs the dev server on :3100. The service takes out/.render-lock per request (re-entrant when an
  ancestor such as with-render-lock holds it), closes Chromium after each request (REMATCH_KEEP_WARM=1
  keeps it) and exits when the eval ends. REMATCH_DEBUG_DIR=<dir> dumps each warped photo and render pair.

Method
  iter 1: render the full frame at cam.pose, warp the photo into it through the CameraX ray map,
    ALIKED + LightGlue (CPU), lift render keypoints through the xyz buffer (>= 100 m, discontinuity filter).
  Inliers: PoseLib 6-DoF LO-RANSAC at the known focal, 8 px @1600. It tolerates eye error, so near
    points with parallax survive. The rotation is then refitted with the eye FIXED
    (match.solve_rotation, soft-L1); moving the eye is left to WP-D.
  iter k >= 2: re-render the full frame plus 6 (3x2) or 4 (2x2) narrower tile views (vfov ~ 0.6x) at
    the refined rotation, match each one, and merge them with 3 px @1600 dedup. Stop when the median
    change is < 0.5 px @1600 or after 3 iterations.
  Frames: cam.eye and the output world are in frameOrigin's ENU frame (the geodesy.ts EnuFrame
    convention). The eval passes the GT scene frame (lat/lon = GT, alt = GT eye), so
    world_concord = world_engine - [0, 0, eyeAlt] exactly.

API deviations (additive only)
  RematchRequest adds photoId (required in v0.1: ad-hoc photos are not implemented), frameOrigin,
    maskMode ("drop" default | "lift"), minRangeM, maxKp, url, signal.
  RematchInlier adds depthM, liftM, iter, view.
  RematchIteration adds nMatches, nLower, views, perView, changePx, ms, mask.
  RematchResult adds cam (refined), renderEye, timingMs, notes, version.
  resPx is the residual (px @1600) under the returned refined cam.
  Plan said FastAPI; fastapi/uvicorn are not in the matcher venv, so the service uses stdlib
    http.server (no new deps).

  The signed dy goes from about 0 to -4…-8 px with the lift, so the lift overcorrects. A satellite
  match on a tree crown or roof does not correspond to the top of the object as the photo sees it
  side-on. The service default was therefore set to maskMode "drop" (a dev-only decision). The
  a-priori lift constants (forest 20 m, building render_height) were not tuned.

    measurable on 7033, 6971 and 7018: 0 lower-half inliers in both iterations, because the lower half
    is a person, foreground grass or lake that the DEM render cannot match. FAIL as a blanket criterion.
  >= 2 more quadrants covered: FAIL on all 5 (iter2-iter1 quadrant gains 0, +1, 0, +1, 0 for 7033, 7131, 6971, 7018, 7053).
    7131 started with 3 of 4 quadrants, so +2 was impossible. The tiles mainly add density in
    quadrants that are already covered.
  Masking reduces the median lifted-point error in villages (building points; no interior dev pins
    exist, so the reference is the GT camera, which is fitted to the control pins, plus the loop's
    refined camera):
    - Lift mode: FAIL. Worse in 3/3 photos with buildings under the refined reference, and in 2/3
      under GT.
    - Drop mode: small gains on all<5 km under the refined reference (7033 3.2 -> 2.8, 7131
      3.6 -> 3.5, 7018 6.4 -> 6.1, 6971 3.8 -> 3.8). It is not a per-building measure, since the
      dropped points are then absent. Weak PASS at best.
    - PENDING the blind interior pins in villages (WP-A).

  Report latency: DONE (above).

Known issues
  - Renders come from the app eye (render_worker has no eye override and was not edited). Lifting and
    residuals use cam.eye exactly, so only render appearance/parallax differs (7053: 12.2 m, in notes).
  - Render-match vs GT: on 7018 every inlier band sits at dx ≈ -6 px under the GT pose, and the
    refined yaw is 159.92 vs GT 160.21. The independent :8765 matcher also finds 159.86 (results.json).
    So this is a real imagery/GT disagreement, not a WP-G bug. WP-D should weight render-match cues
    against the pins accordingly.
  - 7018 and 7033 iter 1 at full frame gets few matches (10 and 73): hazy lake views. The tiles recover
    them (256 and 382).
  - Ad-hoc (non-bundled) photos are not supported: photoId is required.
  - Mask classes are Swiss only (swisstopo tiles). Elsewhere the mask is a no-op (tiles = 0 in the
    iteration mask stats). Overpass (the plan's OSM source) returned 504 throughout this session.
  - The quadrant criterion probably needs rewording (e.g. "bands" or cells of a 4×3 grid). The
    tiles cannot create matches in foreground/person/water regions.
