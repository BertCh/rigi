## 5. API concepts
- Layering (PR #3250): `GPUProgram` (semantic ops + reusable primitives + concrete `GPUCommandNode`s) --transform--> `GPUCommandGraph` --compile/encode--> WebGPU. "Rich arisia.gl program vocabulary -> small generic command vocabulary -> WebGPU"; no mirrored command class per semantic op.
- `GPUOperationLoweringRegistry` maps semantic op types to backend lowerers; compiler records `compilation.lowering.decisions` ("why was this realization selected"); `graph.operationLowering` returns operation tree + lowered command nodes with root-to-leaf paths (provenance). Backend capability contract: backend, GPU-resident conditionals, native semantic loops, child executable graphs (WebGPU: conditionals yes, loops/child graphs no; CUDA Graphs hypothetically yes). WebGPU loops lower to bounded expansion + GPU-written indirect dispatch gates; runtime predicates without geometry are compiler errors (no silent CPU readback).
- Execution primitives implement `getCommandNodes(graph)`; decision recorded as `explicit-command-nodes`; construction may allocate graph-owned scratch but must not schedule.
- `Kernel` = lightweight compute executor (complete bindings per dispatch, incl. indirect). Replaces `Computation` in GPU core. `GPUVector`/`GPUVectorLike`/`GraphVectorView` chunked borrowed-buffer views; `GPUValueArena`, `GPUScalar`, transient lifetime planning; readback ring is in the older GPU-core roadmap (Tranche 4.2), not Arisia-specific.
- Solvers: GPUJacobiPCG, createGPUConjugateGradientProgram, GPUDotProductScalar, GPUFloat32HierarchicalReduction, GPUAdaptiveSpMV / GPUProgramSpMV, GPUCOOToCSR, GPUFFT2D.
- Fragmentation: cost model above; "source repacking remains an explicit application choice".

- Not implemented anywhere on GitHub: the branch is empty; the word "Ploor" appears only twice in master, both in gpu-core lowering docs: "decision record is the beginning of the planner/compiler interface that Ploor can later own without changing GPUProgram or GPUCommandGraph" and "Ploor planning/execution boundaries" as a future consumer of provenance.
- Inferred meaning: Ploor = future planner/scheduler (shared execution planner across compiled plans; also cited as "a later shared execution planner can reuse scratch across plans"), and the inspector is its visualization: explain a compilation as a tree of semantic ops with chosen lowering + reason (example in docs: PCG > loop "gpu-gated bounded sequence, WebGPU has no native graph loop"; SpMV "subgroup-row, short-row CSR + subgroup support"; reduction "hierarchical, N exceeds single-workgroup"), plus semantic timing/memory attribution (PCG: SpMV 0.42 ms, reductions 0.19 ms, updates 0.08 ms), generated WGSL navigation, fusion diagnostics, arena/lifetime diagnostics. No UI spec exists; treat it as a text/tree inspector concept.
