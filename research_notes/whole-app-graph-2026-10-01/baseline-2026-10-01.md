# WAG W0.6: re-baseline at master 8351c5a (2026-10-01)

Data only, plus new probes. No runtime `src/` behaviour was changed.

- Commit: `8351c5a` (detached clone of master; the sandbox has no source edits besides the new scripts listed below).
- Machine: Apple M3 Pro, 36 GiB, macOS (Darwin 23.1.0), Node v22.20.0, Playwright Chromium headless shell 1243 (ANGLE/Metal, WebGPU on), headless, one page at a time.
- Server: `vite dev` (DEV build: React `jsxDEV`, un-minified, HMR sockets blocked in the benches that use `routeWebSocket`), own port 3124, config `vite.sb.config.ts` in the sandbox (needed only because the sandbox `node_modules` is a symlink: it widens `server.fs.allow`; not part of the patch).
- Every step ran under `node scripts/gpu/with-render-lock.mjs --` with `RENDER_LOCK_EXCLUSIVE=1` (all slots), except the haze overflow probe (counts, not timings). The lock was shared with other sessions' jobs; they were never killed.
- Renderer: every browser step pins its engine. App-level steps: `?renderer=webgpu` (and `deck` for the comparison). Bench-page steps run the kernels on the WebGPU compute device (no app engine). `look-bench` captures its inputs from the WebGL deck engine (its default; see "look-bench" below for why not webgpu).
- "n" is the number of samples in the median/p90 (photos x runs, or reps). Per-run medians are listed where a bench was repeated 3x, to show the spread. p90 is the nearest-rank 90th percentile of those samples.
- Raw JSON (not committed): `out/baseline/` and `out/baseline/raw/` in the sandbox, paths listed at the end.

## Headlines

1. **The unexplained 67 ms in the sky worker is the tail of ORT's GPU inference, not refine.** `ort.run()` resolves when its work is enqueued; the GPU work finishes later, and the first thing that waits is the refine stage's readback. Draining the queue before `refineSkyGpu` moves it: drain median 67.7 ms, `refineSkyGpu` 4.0 ms (matches the 3.5 ms isolated figure). ORT's real cost is therefore about 16 ms (visible) + 68 ms (GPU tail) = about 84 ms of the 90 ms worker total; refine is 4 ms and the RGB planes 2 ms. See "sky worker profile".
2. **GPU splat sort is broken at 8351c5a on this Chromium**: `splatsort-scan-totals` binds `[p, base]` but its WGSL never reads `p`, so the auto layout has no binding 0 and Dawn rejects the bind group ("binding index 0 not present in the bind group layout"). `GpuSplatSorter.sort()` then fails, which the layer turns into the worker fallback. Reproduced with the sorter directly on the compute device (`--unpatched`). Timings below are with `_ = p;` injected into that kernel via a route (repo untouched). Not fixed here (no runtime change).
3. **Haze head overflow**: 0 of 152 observed fits overflowed (19 photos, 8 fits each). The overflow is a photo-switch effect: simulating the adaptive rule over all 342 ordered photo switches gives 68 overflows (19.9 %), almost all after a low-sky photo (IMG_4703, IMG_6971, IMG_4527, IMG_7130) followed by a normal one. This is the number the W1.4 decision needs.
4. **Photo-view VRAM is still about 2x on WebGPU**: 370 MiB vs 189 MiB (WebGPU vs WebGL deck), 71 vs 8 MiB of that in buffers.
5. **Photo open to data-ready**: WebGPU 4.07 s median (all 57 opens) vs deck 4.26 s; no WebGPU regression. 6 of 19 dev photos fail the script's error check on BOTH renderers (404s / the matcher CORS error), see "app-load".
6. **Main-thread long tasks on photo open** are the same on both renderers: about 3-4 tasks, 460 ms total, one of about 250 ms at 1.5-2.4 s that the CPU profile names as MediaPipe tasks-vision WASM (person segmentation, mostly shader compile `glUseProgram`), plus DEM decode/`countJumps` and tile-cache `put` in bursts of 50-160 ms.

## sky worker profile (new: `scripts/gpu/sky-worker-profile.mjs`)

An instrumented copy of `sky.worker.ts` is served through a Playwright route (the repo file is untouched). Every call in `segmentWith` is wrapped with a timer; the sub-stage list returns on `ms.sub`. Variant `drain` inserts `await queue.onSubmittedWorkDone()` just before `refineSkyGpu`. 3 photos (IMG_6958/7086/7155, 2048x1536 files, worker working size 1024x768, ORT on the shared device, CPU prep path `inferSkyModel`), 6 timed reps each, 3 runs, n = 9 photo-medians.

| variant | stage / sub-stage | median / p90 ms |
|---|---|---|
| plain | total | 88.7 / 178.9 |
| plain | infer stage (= `inferSkyModel`, ORT `run()` enqueue + CPU prep) | 18.3 / 21.7 (sub 16.3 / 18.6) |
| plain | refine stage | 68.5 / 153.5 |
| plain | of which `refineSkyGpu` call (includes waiting on ORT's GPU work) | 68.5 / 153.5 |
| plain | `rgbPlanes` (CPU) | 2.2 / 2.6 |
| drain | queue drain before refine | **67.7** / 149.9 |
| drain | `refineSkyGpu` after the drain | **4.0** / 8.6 |
| drain | total | 91.5 / 178.9 |

Reading: ORT's GPU execution is not finished when `run()` returns (infer shows about 17 ms); about 68 ms of GPU work remains and is paid by the first synchronising call, the refine's readback. The refine itself costs about 4 ms, equal to the isolated graph bench (4.5 ms here). So a graph that keeps ORT output, refine and mask on one device would NOT remove the 67 ms: it is ORT's own GPU time. What could shrink it is ORT (model, fp16, input size), or hiding it behind other work (the stage can overlap if nothing waits on it). The p90 column is the slow first run (about 150 ms drain), see sky-bench. Not covered: the CPU-visible split inside `ort.run()` and `prepareGpu` (that path is the opt-in GPU prep; `req.bitmap` was not used by the bench, so `prepareGpu` never ran).

## Haze head overflow (new: `scripts/gpu/haze-overflow-probe.mjs`), counted from outside

How: a Playwright route serves `src/lib/gpu/look/haze-graph.ts` with a recorder appended that wraps the exported `hazeGraphStats` properties in accessors (no src change; `hazeGraphStats` is already exported, its `tail` flag says whether the first read overflowed). The probe switches the engine to the `photo-matched` preset (`airlight: "fitted"`, the only style that fits haze) in the replace look, then nudges the yaw 6 times (1.5 s each); 8 fits per photo, a fresh page (empty adaptive fraction) per photo, N = 196 611 (512x384 geometry grid; IMG_4703 166 400).

**Observed (within one photo)**: 152 fits over 19 photos, 0 overflows. The first fit on a device uses `0.27 N + 512` slots (53 597) against totals of 1 872-17 154 (0.011-0.087 N); later fits use `1.5 f N + 1024` and stay at 0.65-0.76 of the head at most.

**Simulated (photo switches on one device)**: from each photo's last total/N, the head `headFor` would give the next photo, over all 342 ordered switches:

| | switches | overflows | rate |
|---|---|---|---|
| all ordered photo pairs | 342 | 68 | 19.9 % |
| both photos with sky fraction >= 0.04 (the "normal" photos) | 182 | 4 | 2.2 % |

Sources of the 68: IMG_4703 (16), IMG_6971 (15), IMG_4527 (15), IMG_7130 (14), IMG_7108 (4), 4 others (1 each): photos with totals of 0.011-0.028 N, which make the next head too small for a 0.05-0.087 N photo. Overflow size: 29 to 12 812 slots over (median 4 584, i.e. 18 KB of a 2 x 4 B list pair): one extra tail read of 36 KB at most. Not simulated: real user photo-switch frequency (every ordered pair is equally likely here), a changed window size (N), and the effect of the fit seeing the same photo again.
