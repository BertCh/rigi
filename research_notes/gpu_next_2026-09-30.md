# GPU compute toward luma/deck "next" (2026-09-30)

*Update (2026-10-01): historical. The luma 10 landing in "Remaining work" item 4 happened: the app runs on vendored luma `10.0.0-alpha.2-rigi.2` (d0969e2, c5b2aa1), the `requestDevice` limits patch became #3312/#3313 `requiredLimits` + `attach` (d79ed36), and `ComputeGraph` is the only GPU compute path (042ea54). The three.js renderer and the `src/lib/three-webgpu` spike were removed (583e2b7). Current state: [reports/status.md](../reports/status.md) and `src/lib/gpu/core/README.md`.*

This note follows `gpu_compute_plan_2026-09.md`. The aim is to position the compute side for luma/deck "next", where WebGPU is used everywhere, while staying on luma 9.4.2. deck 10 is not published, and luma 10.0.0-alpha.2 has broken packaging. A separate workstream is porting the deck renderer to WebGPU (`src/lib/deck/**`, `src/lib/deck-webgpu/**`). This note covers only `src/lib/gpu/**` and `scripts/gpu/**`.

**Decision.**
- Every kernel now runs on one shared layer, `src/lib/gpu/core`.
- `@luma.gl/gpgpu/gpu-core` (GPUCommandGraph, GPUReduction, GPUSort, …) is imported only through `core/luma.ts`.
- The compute device can be the renderer's own WebGPU device (`adoptRenderDevice`). Otherwise it is the sidecar.
- The CPU twins stay the reference, and `?gpu=off` still disables everything.

The CPU timings are unchanged throughout. The main gains come from these changes:
- **Readback.** Smaller readbacks and no temporary staging buffers (haze, skyglobal).
- **Warm-up.** Kernels are warmed asynchronously (skyglobal cold, look first pass).
- **Caching.** Repeat calls hit caches (unknown-pose scenes, align edge planes).

The steady-state kernels themselves were already fast.

## Environment notes

- **Port 3110.** It served a different snapshot of the tree during this work, so every run used a private server on this tree (`npx vite dev --config scripts/gpu/vite.gpu.config.ts --port <free>`, `APP_URL=…`).
- **Vite cold dependency cache.** The first import of `@luma.gl/gpgpu/gpu-core` triggers a dependency re-optimisation. The page then loads chunks from before and after it, and `@luma.gl/core` appears twice ("luma.gl has already been initialized"). `GPUReduction.destroy` then throws in `PipelineFactory` (`instanceof` fails), so the first `core-selftest` failed on `graph-reduction`. A rerun passed 13/13. The fix is to add `@luma.gl/gpgpu/gpu-core` to `optimizeDeps.include` in `vite.config.ts`. That file is not owned by this work, so it is listed under follow-ups. This matters once the app calls a `ComputeGraph` (the texture path).
- **zsh.** It does not word-split an unquoted `$VAR`. Pass photo ids to the scripts as separate words.

## Remaining work

1. **Sky-worker ORT device sharing.** Sky segmentation runs ONNX Runtime Web in `src/lib/sky/sky.worker.ts` with the `webgpu` execution provider (`sky/model.ts`), so ORT creates a third WebGPU device, and it lives in the worker. A `GPUDevice` cannot cross realms. Sharing therefore means one of two things:
   - running the mask consumers (`look/textures.ts` masks) in the sky worker on ORT's device (ORT exposes it as `ort.env.webgpu.device`, and `adoptRenderDevice` would need a luma wrapper around it), or
   - giving ORT the render device on the main thread.

   Either way the P(sky) mask would stay on the GPU instead of being read back and uploaded again. This needs the owner of the sky code. Check ORT's limits and features against `RAISED_LIMITS` first.
2. **Wiring the solve grid into the cascade** (needs the app-pipeline maintainers). The steps are in `src/lib/gpu/solve/README.md`:
   - `coarseStage` / `solvePoseAsync` in `geo/solve.ts`,
   - `cascadeAsync` in `geo/pipeline.ts`,
   - opt-in in `unknown-pose.worker.ts`.

   This saves 1.7–4.8 s per focal seed on the no-heading / no-gravity cases. `solve/cpu.ts` duplicates `solveOnce`'s `coarseCost` until geo exports it.
3. **gpu-raster evaluation** (needs a dependency approval). Not started. It would add a new package, which needs the user's approval before install. Nothing in this work depends on it.
4. **Luma 10 migration checklist** (on the bump, when deck 10 ships with a working luma 10):
   - Bump `@luma.gl/*` together, and re-alias any renamed gpu-core exports in `core/luma.ts` only.
   - Drop the workarounds listed in the `core/luma.ts` header if luma 10 provides them:
     - the `ComputePass.setBindings` duck-typing (`core/kernel.ts`),
     - the raw `createComputePipelineAsync` (`kernelAsync`),
     - the adapter `requestDevice` patch for raised limits (`core/device.ts`),
     - the raw `clearBuffer` (`core/pool.ts`),
     - the custom MAP_READ slots, if luma's readback no longer allocates per call.
   - Check whether `GraphDataView` still needs 256-byte-aligned offsets, and whether `ComputeGraph.run` can read transients.
   - Rerun, in order, comparing against `out/gpu/core/before` or the latest profile JSON on non-timing fields:
     - `core-selftest`,
     - every bench (horizon, eye, unknown-horizon, w2-align-parity on three and deck, look, skyglobal, textures, solve),
     - `eval-app` GPU on vs off.
   - Remove the adopt duck-typing in `src/lib/deck-webgpu/device.ts` (`adoptForCompute`). `adoptRenderDevice` is now exported, so this can happen now.
5. **Smaller items:**
   - Nothing calls `releaseSkyGlobalGpu` yet. The grid keeps about 32 MB pooled between calls.
   - The subgroup colour-stats kernel assumes subgroups are contiguous runs of `local_invocation_index`, which WGSL does not guarantee. Resolved: it is now opt-in (it measured no faster at ~1 ms), and each subgroup checks the layout and writes -1 partials when it fails (a negative count; not NaN, which WGSL rejects as a constant and may optimise away); `bandStatsGpu` then re-runs the plain kernel. The texture path cannot see the flag without a readback, so it also defaults to the plain kernel.
   - The compact haze tail read is untested at runtime (the bench photos never overflow the estimate).
   - The scene-profile cache key is the terrain's identity plus its tile count.

## Follow-up: deck-webgpu target formats (2026-09-30, later)

The deck WebGPU targets (`src/lib/deck-webgpu/targets.ts` `TARGET_FORMATS`):
- geometry: rgba32float, xyz ENU plus w = range, 0 = sky;
- colour: rgba16float, linear, premultiplied;
- photo: rgba8unorm-srgb with mips;
- all targets have row 0 at the top.

The geometry, colour and row-order conventions already matched the texture path. The photo format did not. `TEX_PHOTO` now accepts rgba8unorm-srgb and re-encodes RGB to the stored sRGB byte after `textureLoad`'s decode.

textures-bench (`--tag srgb`, IMG_7086/6958/7018) is exact on every pass. It compares the real photo uploaded as -srgb against the array path, and a synthetic photo cycling all 256 byte values per channel as -srgb against rgba8unorm; the diff is 0 in both.
